🧪 DVWA LAB WRITEUP

I tested DVWA like a real attacker. Then I fixed it like a defender.

I practiced common web attacks in a safe, legal lab on my own computer. No real website was attacked. For each test, I show what I tried, what happened, and how to fix it.

SAFE LAB ONLY  •  LOW / MEDIUM / HIGH  •  NO REAL TARGETS

Lab Setup

Lab: DVWA - Damn Vulnerable Web Application, run locally

Goal: Find the weakness, prove it works, then explain the fix in simple English

Rules: Only my own lab. No real websites, no real passwords, no real data.

Levels tested: Low, Medium, and High, where the fix changes the result

Full Test Reports

Read 1 test at a time. Each one follows the same pattern: Goal, What I Did, What Happened, How To Fix It.

1. SQL Injection

LOW • MEDIUM • HIGH

GOAL

Can I trick the database into showing data I should not see?

WHAT I DID

  • Opened SQL Injection page, entered a normal User ID: 1
  • Then tried: 1' OR '1'='1
  • Then tried: 1' UNION SELECT user, password FROM users #

WHAT HAPPENED

At Low, it showed all users. At High, the same input was blocked. This proves the code was not checking user input safely at Low level.

HOW TO FIX IT

Use prepared statements, never build a database query with raw user input, and give the database user only the permission it needs.

2. Reflected XSS

LOW • MEDIUM • HIGH

GOAL

Can I make the page run my own script from a link?

WHAT I DID

  • Entered my name normally, it showed: Hello, John
  • Then tried: <script>alert(1)</script>

WHAT HAPPENED

At Low, a popup appeared, the script ran. At High, the script was cleaned and shown as plain text, no popup.

HOW TO FIX IT

Escape all user input before showing it on the page, and use a strict allow-list for what is allowed.

3. Stored XSS

LOW • MEDIUM • HIGH

GOAL

Can I save a bad script so it runs for every visitor later?

WHAT I DID

  • Left a guestbook message with a script tag inside it
  • Refreshed the page, and visited it again later

WHAT HAPPENED

At Low, the script ran every time the page loaded, for anyone who opened it. This is more dangerous than Reflected XSS because it stays saved.

HOW TO FIX IT

Escape and clean all saved messages before storing and before showing them, and limit the length and characters allowed.

4. Command Injection

LOW • MEDIUM • HIGH

GOAL

Can I run a system command through the ping box?

WHAT I DID

  • Entered a normal IP: 127.0.0.1, it pinged fine
  • Then tried: 127.0.0.1; whoami
  • Then tried: 127.0.0.1 && dir

WHAT HAPPENED

At Low, it ran my extra command and showed the result. At High, only a valid IP was allowed, my extra command was ignored.

HOW TO FIX IT

Never pass user input straight to the system. Check it is a real IP address first, and use safe code that does not use a shell.

5. Brute Force

LOW • MEDIUM • HIGH

GOAL

Can I guess a weak password by trying many times?

WHAT I DID

  • Tried the login page with a small wordlist of common passwords in my own lab
  • Counted how many tries were allowed, and if there was a delay or lock

WHAT HAPPENED

At Low, I could try again and again with no delay. At High, tries were slower and the account was protected better.

HOW TO FIX IT

Lock the account after a few wrong tries, add a delay, add CAPTCHA, and force strong passwords plus 2FA.

6. CSRF - Change Password

LOW • MEDIUM • HIGH

GOAL

Can a bad link change a logged-in user's password without them knowing?

WHAT I DID

  • Opened the Change Password page while logged in
  • Built a link with the new password inside it, and opened it in a new tab

WHAT HAPPENED

At Low, the password changed just by opening the link, no extra check. At High, it asked for the current password and a secret token, so the link alone failed.

HOW TO FIX IT

Use a secret CSRF token on every form, ask for the current password before changing it, and check the token on the server.

7. File Upload

LOW • MEDIUM • HIGH

GOAL

Can I upload a dangerous file instead of a normal image?

WHAT I DID

  • Uploaded a normal .jpg first, it worked
  • Then tried to upload a test script file with a .php ending

WHAT HAPPENED

At Low, the file was accepted with no real check. At High, only real images were allowed, and the file type was checked properly.

HOW TO FIX IT

Check the real file type, not just the name, allow only images, rename the file, and store uploads outside the website folder so they cannot run.

What I Learned

1. Most attacks start with the same mistake: trusting user input without checking it.

2. Low level in DVWA is not how a real site should work, it shows what happens when there is no fix.

3. High level does not mean perfect, it means the easy attack is blocked, and the attacker must work much harder.

4. A good fix is simple: check input, escape output, use tokens, and limit what a user can do.
